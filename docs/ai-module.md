# ИИ-модуль деловой игры «Ситуационное руководство»

Модуль обеспечивает раунды 2 и 3: участник ставит задачу «виртуальному
сотруднику» ресторана, тот отвечает из роли, а по окончании диалога ведущий
получает оценку в процентах с разбором — что сделано верно, что нет и почему.

Главное архитектурное требование заказчика: **подходы должны быть заменяемыми и
сравнимыми**. Поэтому конвейер разбит на четыре этапа, каждый со своим реестром
реализаций, а каждый диалог хранит вариант, под которым он проходил.

---

## Из чего состоит

| Пакет | Ответственность |
| --- | --- |
| `@acme/game` | Методология в чистом виде: уровни, стили, матрица «уровень × новизна задачи», критерии, рубрика оценки, симуляция результата заказа, справочник ресторана. Ни одного вызова модели или БД. |
| `@acme/ai` | Конвейер и подходы: провайдер модели, четыре реестра стратегий, варианты, телеметрия. |
| `@acme/eval` | Офлайн-стенд: размеченные сценарии, метрики, прогон нескольких вариантов и отчёт. |
| `@acme/api` | oRPC-роутеры `game.*` и `admin.game.*`, событийный лог, проекции. |
| `@acme/db` | Схема Postgres: справочники, сессии, заказы, диалоги, события, оценки, варианты. |
| `apps/app` | Экран участника (голос + чат) и экран администратора (разбор, сравнение подходов). |

## Конвейер

```
реплика руководителя
        │
        ▼
 ┌─────────────────┐   heuristic │ llm
 │ engagement      │   «обратились ли к сотруднику»
 └────────┬────────┘   отказ здесь = ход бесплатный
          ▼
 ┌─────────────────┐   prompt-baseline │ rag-lexical │ graph-rag │ …
 │ knowledge       │   «что персонаж знает»
 └────────┬────────┘
          ▼
 ┌─────────────────┐   prompt-baseline │ skill-rl │ …
 │ persona         │   «что персонаж говорит»
 └────────┬────────┘
          ▼
 ответ сотрудника + телеметрия (токены, задержка, стоимость)

завершение диалога
          ▼
 ┌─────────────────┐   rules │ llm-judge │ hybrid │ …
 │ evaluation      │   «как это оценить»
 └────────┬────────┘
          ▼
 оценка 0–100 + раскладка стилей + критерии + результат заказа
```

Ключевой инвариант: **арифметика оценки одна на все подходы**. Стратегия
оценки решает только, *что она увидела* в диалоге (раскладку стилей и
выполненные критерии); проценты считает общая рубрика `scoreDialog` из
`@acme/game`. Иначе два варианта различались бы ещё и способом счёта, и
сравнение ничего бы не значило.

### Что уже реализовано

**engagement**

- `heuristic` — маркеры речи: имя, вопрос, прямое поручение. Ноль стоимости и задержки.
- `llm` — решает модель: ловит косвенную адресацию («пусть десертный цех берёт торт»), но платит вызовом за каждую реплику, включая те, что в heuristic были бесплатными.

**knowledge**

- `prompt-baseline` — весь профиль и карточка заказа в промпт. Контрольная группа.
- `rag-lexical` — TF-IDF-поиск по базе знаний, в промпт попадает только релевантное.
- `graph-rag` — обход графа «сотрудник → уровень → компетенция → тип задачи → правила» с производными фактами.
- `hybrid-rag` — BM25 (K1 = 1.5, B = 0.75) плюс плотные эмбеддинги, слияние
  рангов через RRF (`1 / (60 + rank)`). Складывать сырые очки нельзя: BM25 не
  ограничен сверху, косинус лежит в 0…1. Контроль для всех retrieval-техник.
- `hyde-rag` — перед поиском один low-effort вызов пишет гипотетический
  документ; плотный канал ищет по нему, лексический — по исходной реплике.
- `contextual-rag` — каждый чанк один раз обогащается LLM-подписью до
  индексации; ключ кэша включает провайдера, модель и режим поиска, а в
  промпт роли уходит оригинальный текст без подписи.
- `rerank-rag` — широкий пул (`topK × candidateMultiplier`), затем один вызов
  модели возвращает порядок индексов; сломанный ranking означает откат к
  детерминированному top-K первого этапа.
- `corrective-rag` — грейдер выдаёт вердикт `correct/ambiguous/incorrect` и
  уверенность; при слабой выдаче выполняется ровно один поиск по переписанному
  запросу, без agent-loop.

**persona**

- `prompt-baseline` — один структурированный вызов модели на реплику.
- `skill-rl` — поведение собирается из именованных навыков («переспроси», «сигнализируй о перегрузе», «сопротивляйся микроменеджменту»), выбор навыков обучается контекстным бандитом на награде после диалога.
- `self-consistency` — 3–7 параллельных ответов, консенсус по полям (мода для
  готовности и точек контроля, медиана эмоции, порог большинства для запросов);
  произносится реальный текст ближайшего к консенсусу кандидата.

**evaluation**

- `rules` — детерминированные эвристики речи, ноль обращений к модели.
- `llm-judge` — модель классифицирует стиль и критерии по расшифровке.
- `hybrid` — эвристики как приоритет, модель как арбитр, откат на правила при пропусках.
- `debate-judge` — критик, защитник альтернативы и арбитр последовательно, плюс
  независимая проверка критериев параллельно; в разбор попадают только цитаты,
  буквально найденные в речи руководителя.

### Встроенные варианты

| id | engagement | knowledge | persona | evaluation |
| --- | --- | --- | --- | --- |
| `baseline` | heuristic | prompt-baseline | prompt-baseline | rules |
| `baseline-judge` | heuristic | prompt-baseline | prompt-baseline | llm-judge |
| `llm-first` | **llm** | prompt-baseline | prompt-baseline | llm-judge |
| `rag` | heuristic | rag-lexical | prompt-baseline | hybrid |
| `hybrid-rag` | heuristic | hybrid-rag | prompt-baseline | hybrid |
| `graph-rag` | heuristic | graph-rag | prompt-baseline | hybrid |
| `skill-rl` | heuristic | graph-rag | skill-rl | hybrid |
| `hyde-rag` | heuristic | **hyde-rag** | prompt-baseline | hybrid |
| `contextual-rag` | heuristic | **contextual-rag** | prompt-baseline | hybrid |
| `rerank-rag` | heuristic | **rerank-rag** | prompt-baseline | hybrid |
| `corrective-rag` | heuristic | **corrective-rag** | prompt-baseline | hybrid |
| `self-consistency` | heuristic | prompt-baseline | **self-consistency** | rules |
| `debate-judge` | heuristic | prompt-baseline | prompt-baseline | **debate-judge** |

Варианты отличаются от своего контроля по одному этапу за раз — иначе разница в
метриках не отнесётся ни к одному изменению. Контроль подобран так, чтобы
совпадали остальные три этапа: retrieval-техники сравниваются с `hybrid-rag`,
`self-consistency` — с `baseline`, `debate-judge` — с `baseline-judge`.

Подробный технический разбор каждой из шести передовых техник и baseline-judge
(схемы структурированного вывода, формулы ранжирования, ключи кэша,
порядок вызовов, fallback и телеметрия) лежит в приложении на `/docs/ai` —
там же опубликованы отчёты замеров против классических подходов. Текст всех
системных промптов конвейера и административных ИИ-помощников — отдельно, в
[`docs/llm-prompts.md`](./llm-prompts.md).

## Загрузка документов администратором

Отдельно от вшитого корпуса (`@acme/game`) организация может загрузить свои
PDF/DOCX/TXT через `admin.game.knowledge.*`. Ingestion строит одну
canonical-document текстовую форму и параллельно раскладывает её по трём
хранилищам; retrieval — два сравнимых варианта над этими org-документами,
`org-rag` (дешёвый) и `org-fusion-rag` (широкий), а не один сменивший
другой.

```text
upload PDF/DOCX/TXT → S3
     │
     ▼
extract: Docling → (при отказе/низком качестве) MinerU (PDF) →
         (при отказе) unpdf/mammoth
     │
     ▼
chunk → LLM: audience (character/judge/both) → persist chunk (Postgres)
     │                                              (needs_review → admin
     │                                               подтверждает → ready)
     ▼
fan-out (не блокирует needs_review, свой retry на канал):
     ├─ Qdrant           (embed → векторный канал; читают org-rag и
     │                     org-fusion-rag)
     ├─ Neo4j            (граф сущностей/связей, только non-judge чанки)
     └─ game_knowledge_facts (LLM-триплеты subject/predicate/object,
                               только non-judge чанки)
```

- **Парсинг — трёхуровневый каскад.** `packages/jobs/src/docling-client.ts`
  и `packages/jobs/src/mineru-client.ts` (общий HTTP-контракт —
  `packages/jobs/src/parser-client.ts`) вызывают `services/docling-parser` и
  `services/mineru-parser`. MinerU — второй уровень, только для PDF, только
  когда Docling недоступен или дал `avg_chars_per_page` ниже порога — это
  тяжёлый CPU-пайплайн (минуты, не секунды), не путь по умолчанию. Любой
  отказ каскада откатывается на `unpdf`/`mammoth`, как и раньше. Сервисы
  нужно явно поднять (`docker compose up docling mineru`) и указать
  `DOCLING_SERVICE_URL`/`MINERU_SERVICE_URL` — без них парсинг работает как
  до появления обоих сервисов.
- **audience — обязательный барьер**, а не техника ранжирования: чанк с
  меткой `judge` (методология, критерии оценки) в промпт персонажа не
  попадает никогда. Для Postgres/Qdrant-каналов фильтр стоит в самом
  запросе (`org-rag` и `org-fusion-rag` оба полагаются на
  `searchQdrant`'s audience-фильтр по умолчанию), а не постфактум;
  для Neo4j и `game_knowledge_facts` — сильнее: `judge`-чанки вообще не
  передаются в LLM-экстракцию графа/фактов
  (`packages/jobs/src/trigger/ingest-knowledge-document.ts`), поэтому там
  нет самого запроса, который мог бы забыть фильтр.
  **Известное ограничение**: audience в Qdrant/Neo4j/фактах — снимок на
  момент ingestion. Если админ позже правит audience чанка через
  `updateChunkAudience`, эти три хранилища не обновляются автоматически —
  нужен повторный запуск ingestion (`retry`).
- **needs_review — гейт публикации** для `org-rag`, как и раньше;
  Qdrant/Neo4j/факты индексируются fire-and-forget сразу после него, не
  дожидаясь подтверждения — они дополняют `org-fusion-rag`, не решают,
  виден ли документ вообще.
- **Retrieval — два сравнимых варианта, не один сменивший другой.**
  `org-rag` — плотный поиск по Qdrant, дешёвый контроль. `org-fusion-rag`
  (`packages/ai/src/strategies/knowledge/org-fusion-rag.ts`) — Retrieval
  Gateway: BM25 (org-корпус) + Qdrant + Neo4j (обход от сущностей,
  найденных по совпадению в label — у org-документов нет фиксированной id-
  схемы built-in графа) + атомарные факты, слияние RRF
  (`packages/ai/src/knowledge/fusion.ts`, чистая функция, юнит-тесты без
  живых Postgres/Qdrant/Neo4j) и LLM-реранкер
  (`packages/ai/src/knowledge/rerank.ts`, общий с `rerank-rag`). Ровно те
  же техники (`hybrid-rag`, `rerank-rag`, `contextual-rag`,
  `corrective-rag`) уже измерены на встроенном корпусе в `packages/eval` —
  см. «Что показали замеры передовых техник» ниже — и результат там
  сдержанный: ни одна не дала доказанного улучшения точности, три из шести
  доказанно дороже. `org-fusion-rag` стоит сравнивать с `org-rag` на
  реальных документах организации тем же образом, прежде чем делать его
  вариантом по умолчанию.

## Где здесь эвристики и почему не «всё через LLM»

Регулярные выражения в `@acme/game` живут ровно в трёх местах, и это три разные
роли — заменять их моделью нужно не везде:

| Где | Роль | Есть ли LLM-альтернатива |
| --- | --- | --- |
| Стратегия оценки `rules` | Контрольная группа и работоспособность без ключа API | Да: `llm-judge` и `hybrid`. Достаточно сменить вариант сессии |
| Гейт вовлечения | Решение *до* вызова модели: пока к сотруднику не обратились, ход бесплатный | Да: стратегия `llm`, вариант `llm-first` |
| `game.dialog.screen` | Проверка реплики на грубость *до* отправки в модель | В `llm-judge`/`hybrid` токсичность уже считает модель; регулярка остаётся предохранителем на входе |

То есть «сделать всё через LLM» — это не переписывание, а выбор варианта:

```bash
AI_DEFAULT_VARIANT=llm-first   # в контуре решений эвристик не остаётся
```

Что именно вы за это платите, видно в отчёте стенда и в админской аналитике:
`llm-first` вызывает модель на каждую реплику, включая те, где сотрудник должен
молчать. Поэтому дефолт остался на `baseline`: он работает без ключа API,
воспроизводим и служит опорной точкой. Решение «перейти на LLM везде»
принимается по цифрам, а не по умолчанию.

## Как добавить свой подход

Пример: заменить лексический поиск на векторный.

**1. Написать стратегию.** Единственный контракт — интерфейс этапа
(`EngagementStrategy`, `KnowledgeStrategy`, `PersonaStrategy`,
`EvaluationStrategy`):

```ts
// packages/ai/src/strategies/knowledge/embeddings.ts
import type { KnowledgeStrategy } from "../../types";

export const embeddingsKnowledge: KnowledgeStrategy = {
  id: "rag-embeddings",
  description: "Поиск по векторному индексу (pgvector).",

  async retrieve(request, deps) {
    const startedAt = Date.now();
    const hits = await searchVectorStore(request.query, deps.params.topK ?? 6);

    return {
      snippets: hits.map((hit) => ({
        id: hit.id,
        text: hit.text,
        score: hit.score,
        source: "vector",
      })),
      latencyMs: Date.now() - startedAt,
    };
  },
};
```

**2. Зарегистрировать её** в `packages/ai/src/registries.ts`:

```ts
knowledgeRegistry.register(embeddingsKnowledge);
```

**3. Завести вариант** — либо в `BUILT_IN_VARIANTS`, либо прямо из админки
(`admin.game.variants.upsert`), где id стратегий валидируются по реестрам.

Больше менять нечего: API, UI и аналитика работают с реестрами, а не со
списком известных подходов.

> ⚠️ Правило, которое стоит соблюдать в любой новой knowledge-стратегии:
> **персонажу нельзя показывать методологию**. Документы в базе знаний
> помечены `audience`, и всё, что помечено `judge` (названия стилей, уровни
> готовности, матрица), в промпт роли не попадает. Иначе сотрудник рано или
> поздно подскажет участнику правильный ответ и упражнение сломается.

## Как понять, что подход улучшил игру

Два независимых измерения — и оба нужны.

### 1. Офлайн: размеченные сценарии

```bash
# быстрый дымовой прогон без обращения к модели
bun eval --variants baseline,rag,graph-rag

# содержательное сравнение
bun eval --provider anthropic --variants baseline,rag,graph-rag --out reports/run.md

# обучаемые стратегии: несколько эпох с обратной связью
bun eval --provider anthropic --variants baseline,skill-rl --epochs 5 --learn
```

В `packages/eval/src/fixtures.ts` лежат сценарии с разметкой: ожидаемый
стиль, фактический стиль, экспертный балл и список выполненных действий.

Сценарии разбиты на два уровня. `CORE_FIXTURES` (экспортируется как
`FIXTURES`, используется по умолчанию) — 12 сценариев: по одной ситуации на
каждую пару «ожидаемый стиль × попадание/крайний промах», раунд 2 и раунд 3,
где методология вообще допускает раунд 3. Этого достаточно, чтобы поймать
явную регрессию, и ровно этот набор реально разметить экспертно целиком, а не
частично. `EXTENDED_FIXTURES` (ещё 8, вместе — `ALL_FIXTURES`, флаг
`--extended`) — «промах на одну ступень», нужны только для финальной проверки
перед решением о внедрении, где важен частичный кредит из `styleCredit`, а не
факт «сработало / нет».

Раньше здесь генерировался плоский пул на 70 сценариев (`gen-fixtures.ts` всё
ещё умеет его собрать, если пул понадобится расширять): один и тот же
конфликт стилей повторялся под 4-5 разными сотрудниками с почти одинаковым
экспертным баллом — тот же сигнал, оплаченный кратно дороже в LLM-вызовах без
дополнительной различающей силы. Текущий отбор — по одному каноничному
сотруднику/блюду на конфликт — убирает эту избыточность.

Отчёт считает по каждому варианту:

- **MAE к эксперту** — головная метрика: насколько автоматическая оценка
  расходится с оценкой ведущего;
- **совпадение ожидаемого/фактического стиля**;
- **F1 по критериям**;
- **выдержана ли роль** — не назвал ли персонаж стиль или уровень;
- **молчание до обращения** — соблюдено ли требование ТЗ;
- **задержка, токены, стоимость**.

> Прогон с `--provider simulated` (по умолчанию) проверяет, что конвейер жив,
> но не сравнивает подходы: симулированный судья — это те же правила, поэтому
> варианты с LLM-судьёй там совпадают с `rules` по построению. Отчёт об этом
> честно предупреждает.

Как считается значимость: сравнение парное по сценариям (разница берётся внутри
сценария и только потом усредняется), 95% интервал — персентильный бутстрап на
10 000 ресэмплов с фиксированным seed, p — двусторонний парный перестановочный
тест со сменой знака. Вывод «лучше» ставится только при пяти и более парных
наблюдениях и интервале, не пересекающем ноль. Диалоги, не доехавшие до оценки,
исключаются из метрик и публикуются числом: иначе вариант мог бы «выиграть»,
уронив именно трудные для себя сценарии.

### Что показали замеры передовых техник

Первый прогон 20 августа 2026 (70 сценариев, 1 повтор на сценарий,
`packages/eval/reports/full-cheap-gpt55*.md`) дал ту же картину, что и
18 августа: у всех шести техник доверительные интервалы пересекали ноль —
«не доказано» везде. Причина видна в самих отчётах: **прогон один на
сценарий не даёт σ внутри сценария** (стенд явно предупреждает об этом),
поэтому весь разброс ответа модели утекает в тот же интервал, что и разница
между вариантами — эффект технически может быть, но тонет в шуме одного
замера.

Второй прогон в тот же день исправил это: **15 сценариев × 4 повтора**
на технику (`packages/eval/reports/precise-*.md`), с усреднением по
повторам перед парным сравнением — это гасит именно ту компоненту шума,
которая душила первый прогон, без роста числа сценариев. `--concurrency 4`
дополнительно сократил время прогона с ~4 часов до ~40 минут на технику.
Результат — уже не шум:

**Вывод изменился по сути, не только по цифрам**: две из шести техник
(`contextual-rag`, `rerank-rag`) статистически доказанно **хуже** контроля —
и при этом заметно дороже по задержке (contextual-rag: 35 с против 171 с
у hyde-rag на первом прогоне; rerank-rag: 106 с против 61 с у hybrid-rag).
Это не «нет данных», это прямая рекомендация не внедрять. `self-consistency`
не столько «не помогает», сколько **невидима для контрольной оценки**:
`rules`-стратегия детерминирована по регулярным маркерам речи и не различает
«один ответ» и «консенсус трёх» — чтобы вообще замерить её эффект, нужен
контроль на `llm-judge`/`hybrid`, а не на `rules`.

`debate-judge` наконец получил данные (после урезания пула до `CORE_FIXTURES`
прогон уложился в 31 минуту вместо часов, throughput не кончился) — и картина
та же, что у RAG-техник: ни точность стиля, ни F1 критериев, ни MAE к
временной калибровке не сдвинулись доказанно, а стоимость диалога выросла
доказанно на 37% ($0.30 против $0.22). Критик + защитник + арбитр
последовательно — это реальные дополнительные вызовы модели, и они не платят
за себя точностью. Пометка отчёта: сравнение идёт против судьи с другой
стратегией оценки (контрольный вариант использует `llm-judge`, кандидат —
`debate-judge`), так что метрики точности здесь шумнее, чем в паре с одинаковым
судьёй — но вывод по стоимости от этого не зависит и доказан отдельно.

Повтор `contextual-rag` против `hyde-rag` на `CORE_FIXTURES` дал **обратную**
картину: точность по-прежнему не доказана в обе стороны, но по стоимости
`contextual-rag` теперь **доказанно дешевле** контроля ($0.25 против $0.35),
а не дороже. Это прямое противоречие первому прогону, и честный вывод — не
«контекстуальный RAG внезапно исправился», а что сравнение чувствительно к
набору сценариев и модели: старый прогон считался на другом (70-сценарном,
удалённом) пуле, другой модели за шлюзом и другой разметке
(`labelSource: provisional`-формула вместо нынешнего `ai-assisted`-прохода) —
слишком много одновременных отличий, чтобы утверждать, какое из них
перевернуло знак. Предыдущий вердикт «доказанно хуже точности» относится
только к исходному 70-сценарному набору и **не подтверждён повторно**: он
не должен приниматься как окончательный без разметки методолога.
Повтор `rerank-rag` против `hybrid-rag` на `CORE_FIXTURES` частично
воспроизвёлся: штраф по стоимости и задержке — тот же, что и раньше ($0.38
против $0.22, 108 с против 57 с), а вот доказанный вред для точности стиля
из первого прогона не подтвердился (точечные оценки теперь даже в пользу
rerank-rag, но интервалы слишком широки на 12 сценариях). Рекомендация не
внедрять остаётся в силе — доплата без доказанной пользы, — но обоснование
сузилось до стоимости, и былую формулировку «хуже, доказано» по точности
повторно доказать не удалось.

`corrective-rag` с удвоенным числом повторов (6 вместо 4, чтобы наконец
задеть ноль — план из пункта 4 ниже) эффект не обнаружен на текущей
выборке — даже с большей мощностью MAE осталась отрицательной (-0.51,
тот же знак, что и в первом прогоне) внутри интервала, пересекающего ноль.
Зато стоимость подтвердилась третий раз подряд как единственный
воспроизводимый эффект передовых retrieval-техник: **хуже, доказано**,
$0.37 против $0.22. Прогон занял почти 2 часа (72 диалога на арм, 1209
успешных вызовов, 4 временных отказа схемы у пула — самовосстановился без
вмешательства). Для окончательного решения необходимы экспертная разметка
и дополнительные сценарии.

Свод по всем шести техникам на `CORE_FIXTURES`: **ни одна не показала
доказанного улучшения точности**, три из шести (`rerank-rag`,
`corrective-rag`, `debate-judge`) доказанно дороже контроля, и только
`contextual-rag` вышла доказанно дешевле — единственный кандидат, для
которого рекомендация отложить внедрение связана не с ценой, а с
отсутствием доказанной пользы.

Ограничение то же, что и раньше: приведённые числа считались на прежнем
70-сценарном пуле, ни один сценарий которого не был подписан методологом
(`labelSource: "provisional"` у всех), поэтому «MAE к эксперту» измеряет
расхождение с временной калибровкой — этого достаточно, чтобы поймать явную
регрессию (что и произошло), и недостаточно для финального решения о

Практические уроки по throughput на этом платном шлюзе (`router.cheap`),
пригодятся при повторе:

- Узкое место — throughput, не квота. Признак — диалоги обрываются пачками
  с ошибкой уровня TCP-соединения («Cannot connect to API», без
  HTTP-статуса), а не 429/`quota exceeded`; единичные ручные запросы к тому
  же ключу в этот момент проходят нормально. `AI_POOL_COOLDOWN_MS` не
  помогает — он рассчитан на несколько кандидатов в пуле, а здесь один.
- Лечится дроблением прогона на изолированные сравнения технология-контроль
  (1 арм против 1 контроля, не все шесть разом) и параметром
  `--concurrency` (по умолчанию 1 — диалоги идут строго последовательно;
  4 сократило 15×4×2 сравнение с ~4 часов до ~40 минут без роста отказов).
- Throughput накапливается по сессии: два прогона подряд без паузы (даже
  разного объёма) исчерпывают его быстрее, чем кажется по одному прогону —
  именно так не хватило на `debate-judge` дважды подряд.

### 2. Онлайн: реальные игры

Каждый диалог пишет `variantId` и телеметрию, поэтому
`admin.game.analytics` (экран `/admin/game`) показывает по вариантам: среднюю
оценку, долю совпадений стиля, долю успешных заказов, покрытие критериев,
среднюю задержку и стоимость диалога.

Экспертной разметки в проде нет — поэтому онлайн-метрики отвечают на вопрос
«что подход сделал с играми», а офлайн-стенд — на вопрос «насколько он согласен
с ведущим». Решение принимается по обеим: подход, который поднял согласованность
на 3 пункта и удвоил стоимость диалога, — это выбор, а не автоматическая победа.

## Методология в коде

Ожидаемый стиль выводится так:

```
базовый индекс уровня (L1→директивный … L4→делегирующий)
  + (компетенция по типу задачи − компетенция, подразумеваемая уровнем)
  − 1, если задача сложная и сотрудник её ещё не освоил
  − 1, если задача максимальной сложности, а сотрудник лишь «уверенно делает»
  ± поправки на нагрузку смены (раунд 3)
```

Смысл второй строки: **уровень уже включает ожидаемую компетенцию**. L2 по
определению «осваивает», поэтому на своей обычной задаче он получает
наставнический стиль, а не директивный. А L4 на новой для себя задаче
проваливается сразу на несколько ступеней — это и есть случай Анны с тортом
из ТЗ.

Оценка складывается из трёх частей: стиль (45), управленческие действия (35),
результат заказа (20), минус штрафы за грубость. Кредит за стиль асимметричен:
недоуправление (делегировали новичку) наказывается сильнее, чем
переуправление, — потому что именно оно портит заказ.

## Надёжность и безопасность

- **Событийный лог.** `game_events` — append-only; состояние диалога и оценка
  это его проекции. Сбой на этапе оценки не теряет расшифровку.
- **Молчание до обращения** проверяется до вызова модели: пустые ходы
  бесплатны, а требование ТЗ выполняется одинаково во всех вариантах.
- **Stay in role.** Правила роли в системном промпте плюс фильтрация базы
  знаний по `audience`; в офлайн-стенде есть метрика нарушений роли.
- **Токсичность.** `game.dialog.screen` позволяет платформе проверить реплику
  до отправки; грубые реплики снижают оценку и мотивацию персонажа.
- **Приватность.** Модуль работает с текстом: аудио остаётся на стороне
  платформы и в БД не попадает.

## Интеграция с платформой

Формат интеграции по ТЗ уточняется, поэтому модуль намеренно ничего не знает
о транспорте: движок stateless, состояние диалога принадлежит вызывающей
стороне. Сейчас поверх него работает oRPC-слой:

| Процедура | Назначение |
| --- | --- |
| `game.catalog.reference` | справочники сотрудников и заказов |
| `game.catalog.methodology` | словарь стилей, уровней, критериев |
| `game.session.create/list/byId/end` | сессии игры |
| `game.order.create/list/setStatus` | очередь заказов и распределение |
| `game.dialog.start` | открыть диалог по заказу |
| `game.dialog.say` | реплика руководителя → ответ сотрудника |
| `game.dialog.finish` | завершить и получить оценку |
| `game.dialog.screen` | быстрая проверка реплики на токсичность |
| `admin.game.dialogs` | список диалогов с оценками |
| `admin.game.analytics` | сравнение подходов на живых играх |
| `admin.game.variants.*` | управление вариантами |

Распознавание речи (STT) остаётся модулем платформы: браузерный ввод в
`apps/app` — это референсная реализация, в API уходит уже текст.
